Большинство сайтов на Next.js, React и похожих фреймворках после первой загрузки выполняют переходы между страницами
с помощью JavaScript, без загрузки нового документа. До сих пор данные Chrome о реальных пользователях (CrUX) эти
переходы не видели: LCP измерял только первую загрузку, а INP и CLS за всю сессию приписывались одному посещению
страницы. 13 октября 2026 года Chrome добавил в CrUX экспериментальные Core Web Vitals, которые учитывают и такие
переходы внутри приложения (soft navigation). В этой статье разбираем, что изменилось, что показывают первые данные
и как проверить свой сайт. Как мы работаем с производительностью в проектах, мы кратко объяснили
[на странице вопросов](/ru/voprosy#faq-performance).

## Что изменилось?

[Согласно анонсу на web.dev](https://web.dev/blog/crux-experimental-soft-navs/), вместе с Soft Navigations API в
браузере Chrome добавил в CrUX три новых экспериментальных поля: версии LCP, INP и CLS, учитывающие переходы внутри
приложения. Данные доступны в BigQuery, CrUX API и CrUX History API начиная с набора, опубликованного в октябре
2026 года. Chrome сообщает, что в следующем выпуске CrUX ожидает добавить метрики soft navigation для типов навигации
и FCP.

[Согласно документации Chrome](https://developer.chrome.com/docs/web-platform/soft-navigations), функция включена по
умолчанию в Chrome 151 и Edge 151 и не поддерживается в Firefox и Safari. Текущие значения Core Web Vitals не
изменились; новые метрики находятся рядом с ними в отдельных полях.

| | Классическое измерение | Измерение с учётом soft navigation |
|---|---|---|
| LCP | Только первая загрузка страницы | Также собственный LCP каждого перехода внутри приложения |
| INP и CLS | Вся сессия приписывается первому посещению страницы | Классическое посещение заканчивается на первом soft navigation, каждый переход считается отдельно |
| Статус | Стабильное, используется в Search Console | Экспериментальное, цель — май 2027 |
| Браузер | Chrome | Chrome и Edge 151+ |

## Что такое soft navigation?

На классическом сайте каждый клик по ссылке заставляет браузер загрузить новый HTML-документ. В одностраничном
приложении (SPA) после первой загрузки браузер остаётся на странице: JavaScript отрисовывает новое содержимое и меняет
URL в адресной строке. Для пользователя это тоже переход на другую страницу, но с точки зрения браузера новая
страница не загружалась.

Чтобы считать переход soft navigation, Chrome проверяет три условия: переход начинается с действия пользователя,
видимый пользователю URL меняется, а после взаимодействия на экране появляется видимая отрисовка. Документация прямо
предупреждает, что такой эвристический подход может давать ложноположительные и ложноотрицательные результаты. В ней
также сказано, что многие JavaScript-фреймворки используют эту модель, но каждый по-своему.

## Почему это было важно?

Для SPA классическое измерение вводило в заблуждение в двух отношениях. Во-первых, переходы внутри приложения вообще
не попадали в LCP, хотя часто они быстрые; LCP сайта сводился к первой загрузке, самому тяжёлому моменту.
Во-вторых, поскольку все взаимодействия и сдвиги макета за сессию приписывались одному посещению, INP и CLS могли
сильно расти в длинных сессиях.

[Согласно документации Chrome](https://developer.chrome.com/docs/web-platform/soft-navigations), при новом подходе
измерение INP и CLS классического посещения заканчивается в момент первого soft navigation, а каждый переход начинает
собственное измерение. LCP перехода рассчитывается только по содержимому, заново отрисованному после этого
взаимодействия.

<Callout type="warn" title="Экспериментальные данные, о ранжировании ничего не сказано">
  В анонсе Chrome не говорится о ранжировании в Google. Новые метрики экспериментальные; Chrome планирует сделать их
  стабильными в мае 2027 года «с учётом отзывов» и затем перевести Search Console на новые данные. Нового порога для
  ранжирования сегодня нет, но ясно, что отчёты Search Console позже будут обновлены этими данными.
</Callout>

## Что это значит для вашего сайта?

| Как устроен сайт | Ожидаемый эффект | Приоритет |
|---|---|---|
| Классический многостраничный сайт (тема WordPress, страницы с сервера) | Почти ничего не меняется | Продолжайте следить за текущими Core Web Vitals |
| Корпоративный сайт на Next.js или React с переходами на стороне клиента | LCP, вероятно, улучшится, INP и CLS станут видны по каждому переходу | Проверьте новые поля в CrUX |
| Интерактивное SPA: панель, приложение, фильтры интернет-магазина | Здесь самые большие изменения; медленные переходы теперь видны в данных | Настройте измерение по переходам |
| Мобильная аудитория преимущественно на Safari | CrUX эту аудиторию не показывает | Настройте собственный мониторинг реальных пользователей |

## Как проверить свой сайт

Если у сайта достаточно трафика, чтобы попасть в CrUX, новые экспериментальные поля можно запросить через CrUX API,
CrUX History API или BigQuery, а наглядно посмотреть в инструменте CrUX Vis. У сайтов с небольшим трафиком данных
CrUX может не быть, и тогда нужно собственное измерение.

В документации Chrome есть несколько практических предупреждений:

- Браузер создаёт отдельную запись производительности для каждого soft navigation; их рекомендуется собирать с
  помощью наблюдателя, потому что буферизованные записи ограничены первыми 50.
- LCP перехода берётся не из стандартной записи LCP, а из записей об отрисовке после взаимодействия.
- Поскольку учитывается только заново отрисованное содержимое, неизменная часть экрана может сделать LCP перехода
  отличным от холодной загрузки.
- Библиотека web-vitals от Chrome сообщает время ответа сервера (TTFB) для soft navigation как 0.
- Из браузеров не на Chromium и из Chrome до версии 151 эти метрики не поступают.

<Callout type="tip" title="Начните с самых частых переходов">
  Не пытайтесь улучшить все переходы сразу. После настройки измерения найдите два-три самых популярных перехода
  (например, из списка товаров в карточку товара или из меню на страницу услуги) и сначала посмотрите на их INP и
  LCP. Большой запрос данных или тяжёлый компонент, загружаемый при переходе, — среди частых причин.
</Callout>

## Чек-лист

| Шаг | Что делать |
|---|---|
| 1. Определите структуру | Переходы на сайте загружают новую страницу или выполняются на клиенте? |
| 2. Посмотрите CrUX | Сравните новые экспериментальные поля LCP, INP и CLS с классическими значениями |
| 3. Проверьте аудиторию | Посмотрите в аналитике долю Chrome и Safari; если преобладает Safari, CrUX неполон |
| 4. Настройте измерение | Добавьте записи soft navigation в собственный мониторинг реальных пользователей |
| 5. Найдите медленные переходы | Составьте список худших значений INP и LCP по переходам |
| 6. Подготовьтесь к маю 2027 | Исправляйте проблемы уже сейчас, считая, что Search Console перейдёт на новые данные |

## Частые ошибки

- **Считать новые значения метрикой ранжирования.** Метрики экспериментальные, а о ранжировании Chrome ничего не
  сказал.
- **Принимать лучший LCP за более быстрый сайт.** Chrome прямо пишет, что скачок у SPA связан с тем, что именно
  измеряется; первая загрузка такая же быстрая, как раньше.
- **Упускать INP.** Сайты с преобладанием SPA отстают от многостраничных по INP; тяжёлый JavaScript во время
  перехода — типичная причина.
- **Полагаться только на данные Chrome.** Пользователи Safari и Firefox в это измерение не попадают.
- **Считать, что учитывается каждый переход.** Определение Chrome требует действия пользователя, видимого изменения
  URL и новой отрисовки, а документация предупреждает о возможных ложноположительных и ложноотрицательных
  результатах.

## Заключение

Метрики soft navigation дают SPA-сайтам то, чего не хватало годами: реальный опыт пользователя при перемещении по
сайту, а не только первую загрузку. Данные экспериментальные, и о влиянии на ранжирование не объявлено, но цель

хорошее время узнать, как выглядят ваши переходы.
