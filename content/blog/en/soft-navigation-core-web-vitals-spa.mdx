Most sites built with Next.js, React or similar frameworks handle page changes after the first load with JavaScript,
without loading a new document. Until now, Chrome's real user data (CrUX) didn't see these changes: LCP measured only
the first load, while INP and CLS were assigned to a single page visit for the whole session. On 13 October 2026,
Chrome added experimental Core Web Vitals to CrUX that also cover these in-app route changes, known as soft
navigations. This post explains what changed, what the first data shows and how to check your own site. We briefly
explain how we handle performance in our projects [on our FAQ page](/en/faq#faq-performance).

## What changed?

[According to the announcement on web.dev](https://web.dev/blog/crux-experimental-soft-navs/), Chrome added three new
experimental fields to CrUX together with the Soft Navigations API in the browser: versions of LCP, INP and CLS that
also cover in-app navigations. The data is in BigQuery, the CrUX API and the CrUX History API from the dataset
released in October 2026. Chrome says it expects to add soft navigation metrics for navigation types and FCP in the
next CrUX release.

[According to Chrome's documentation](https://developer.chrome.com/docs/web-platform/soft-navigations), the feature is
on by default in Chrome 151 and Edge 151, and is not supported in Firefox or Safari. The existing Core Web Vitals
values have not changed; the new metrics sit next to them as separate fields.

| | Classic measurement | Measurement including soft navigations |
|---|---|---|
| LCP | First page load only | Each in-app navigation's own LCP as well |
| INP and CLS | The whole session is assigned to the first page visit | The classic page visit ends at the first soft navigation, and each navigation counts separately |
| Status | Stable, used in Search Console | Experimental, May 2027 target |
| Browser | Chrome | Chrome and Edge 151+ |

## What is a soft navigation?

On a classic site, every link click makes the browser load a new HTML document. In a single-page application (SPA),
the browser stays on the page after the first load; JavaScript draws the new content and changes the URL in the
address bar. For the user it is still a page change, but from the browser's point of view no new page was loaded.

Chrome looks for three conditions to count a navigation as a soft navigation: it must be started by a user action,
the URL the user sees must change, and there must be a visible paint after the interaction. The documentation also
says plainly that this heuristic approach can produce false positives and false negatives. It notes that many
JavaScript frameworks use this model, but each in a different way.

## Why did it matter?

The classic measurement was misleading for SPAs in two ways. First, in-app navigations never made it into LCP, even
though they are often fast; the site's LCP was just the first load, its heaviest moment. Second, because every
interaction and layout shift during the session was assigned to one page visit, INP and CLS could balloon in long
sessions.

[According to Chrome's documentation](https://developer.chrome.com/docs/web-platform/soft-navigations), in the new
approach the INP and CLS measurement of the classic page visit ends when the first soft navigation happens, and each
navigation starts its own measurement. The navigation's LCP is calculated only from content newly painted after
that interaction.

<Callout type="warn" title="Experimental data, no statement on rankings">
  Chrome's announcement does not mention Google Search rankings. The new metrics are experimental; Chrome aims to
  make them stable in May 2027, "subject to feedback", and then switch Search Console to the new data. There is no
  new ranking threshold today, but it is clear that Search Console reports will be updated with this data later.
</Callout>

## What does the first data show?

[According to the CrUX release notes](https://developer.chrome.com/docs/crux/release-notes), the September 2026
dataset covers 18,376,044 sites. When soft navigations are included, the share of sites rated good rises on all four
measures, with the biggest jump on LCP.

Chrome stresses that this jump is not because SPAs are generally faster than multi-page sites: fast in-app
navigations are now being counted. On CLS, SPA-heavy sites come level with multi-page sites on desktop and nearly
match them on Android. On INP, although the Android pass rate roughly doubles, in Chrome's words SPA-heavy sites
still trail multi-page sites in good INP overall.

## What does it mean for your site?

| How your site is built | Expected effect | Priority |
|---|---|---|
| Classic multi-page site (WordPress theme, server-rendered pages) | Almost no change | Keep monitoring your current Core Web Vitals |
| Corporate site built with Next.js or React that changes pages on the client | LCP probably improves, INP and CLS become visible per navigation | Check the new fields in CrUX |
| Highly interactive SPA such as a dashboard, app or e-commerce filters | The biggest change is here; slow navigations now show up in the data | Set up per-navigation measurement |
| Mobile audience that is mostly on Safari | CrUX doesn't show this audience | Set up your own real user monitoring |

## How to check your own site

If your site has enough traffic to appear in CrUX, you can query the new experimental fields through the CrUX API,
the CrUX History API or BigQuery, and look at them visually with the CrUX Vis tool. Low-traffic sites may have no
CrUX data, in which case you need your own measurement.

Chrome's documentation has several practical warnings for this:

- The browser produces a separate performance entry for each soft navigation; collecting them with an observer is
  recommended, because buffered entries are limited to the first 50.
- A navigation's LCP is read from the post-interaction paint entries, not from the standard LCP entry.
- Because only newly painted content counts, content that stays unchanged on screen can make the navigation's LCP
  differ from a cold load.
- Chrome's web-vitals library reports server response time (TTFB) as 0 for soft navigations.
- These metrics don't arrive from browsers other than Chromium, or from Chrome before 151.

<Callout type="tip" title="Start with the most used navigations">
  Don't try to improve every navigation at once. Once measurement is in place, find the two or three most clicked
  navigations (for example, from a product list to a product page, or from the menu to a service page) and look at
  their INP and LCP first. A large data request or a heavy component loaded during the navigation is among the
  common causes.
</Callout>

## Checklist

| Step | What to do |
|---|---|
| 1. Identify the structure | Do your page changes load a new page, or happen on the client? |
| 2. Look at CrUX | Compare the new experimental LCP, INP and CLS fields with the classic values |
| 3. Check your audience | Look at the Chrome and Safari share in analytics; if Safari dominates, CrUX falls short |
| 4. Set up measurement | Add soft navigation entries to your own real user monitoring |
| 5. Find slow navigations | List the worst INP and LCP values per navigation |
| 6. Prepare for May 2027 | Fix issues now, assuming Search Console will switch to the new data |

## Common mistakes

- **Treating the new values as a ranking metric.** The metrics are experimental, and Chrome said nothing about
  rankings.
- **Taking better LCP to mean a faster site.** Chrome says plainly that the jump for SPAs comes from what is being
  measured; the first load is just as fast as before.
- **Overlooking INP.** SPA-heavy sites trail multi-page sites on INP; heavy JavaScript running during a navigation is
  a typical cause.
- **Relying only on Chrome data.** Safari and Firefox users are not in this measurement.
- **Assuming every navigation will be counted.** Chrome's definition looks for a user action, a visible URL change
  and a new paint, and the documentation also says this approach can produce false positives and false negatives.

## Conclusion

Soft navigation metrics bring something SPA sites have lacked for years: the real experience of users moving around
the site, not just the first load. The data is experimental and no ranking impact has been announced, but Chrome's
goal is to switch Search Console to this data in May 2027. If you have a site built with Next.js or React, now is a
good time to find out how your navigations look.
